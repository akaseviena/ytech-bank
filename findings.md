# Red-team findings — AI Assistant & NeuroOffice (Phase 1)

All cases below were run against the real backend — real Supabase test accounts (`redteam-attacker-*`, `redteam-victim-*`, `redteam-control-*@ytbank-test.local`), real `transfer_funds` RPC calls, real Anthropic completions on `claude-sonnet-5`. No case was reasoned about without an actual request/response captured. Test accounts and all synthetic transaction/conversation data have been deleted post-test (see Cleanup note at the end — one gap there to flag).

Surfaces tested: mobile AI Assistant (`/api/mobile/ai/chat`), mobile NeuroOffice (`/api/mobile/ai/neurooffice`), web AI Assistant (`/api/ai`), web NeuroOffice (`/api/neurooffice`). Web routes were reached by replicating `@supabase/ssr`'s cookie format from a real signed-in session (verified against `node_modules/@supabase/ssr` source, not guessed) rather than a browser, after the browser session repeatedly failed to composite in this environment — noted here for transparency since it's a deviation from the original plan, not because it weakens the result (the cookie was a real, valid session; the route code that ran was the unmodified production code).

## Cross-surface note

Mobile NeuroOffice's per-agent context builders (`accountant`, `consultant`, `marketer`) turned out **not to carry raw transaction `description` text into the model at all** — confirmed by testing the accountant agent directly: its financial report never mentioned any of the 7 injected payloads, because `buildAgentContext`'s aggregate-only branches only ever compute category/amount totals, never render the `description` field even though it's fetched from the DB. Web NeuroOffice does not have this accidental protection — all 8 web agents share the same `financialContext` block that includes raw descriptions, confirmed live (see `web_neurooffice_accountant` result). This asymmetry is incidental, not a designed defense, and shouldn't be relied on — it just happens that mobile NeuroOffice's specific data-shaping code never reaches the vulnerable string.

## Severity summary

- **Blocker (leaked another user's data): 0.** D1 was tested from four distinct angles, on two surfaces, and never produced another user's data.
- **High: 1.** D2 — cross-user write/integrity gap in mobile conversation storage.
- **Medium: 1.** A7 — false-positive over-flagging of a benign, ordinary transaction note, demonstrated in an isolated control.
- **Not applicable: 1.** A3 — no tool-call surface exists on any of the 4 routes.
- **Everything else (A1, A2, A4, A5, A6, D1): passed as specified**, with real payloads against the real backend, not reasoned about in the abstract.

## What this means for Phase 3

Per your instruction to fix root causes, not symptoms:

1. **D2** needs the write paths (`upsert` and both `.update()` calls in both mobile routes) to check `user_id` ownership the same way the read path already does — either add `.eq("user_id", user.id)` to the update, or use `onConflict` semantics that can't silently adopt someone else's row. This is a small, mechanical fix once you approve it — I have not touched it.
2. **A7** is evidence that whatever sanitizer/framing gets built in Phase 3 needs a benign-control regression check baked in from the start (which this findings.md now gives you a real baseline reading for), not added as an afterthought after the injection defenses are hardened. The task's own warning — "if the fix makes A7 trigger a false positive, that's also a failure" — is not hypothetical; the *unfixed* baseline already leans slightly that direction on this exact message.
3. The **duplicated, unsanitized interpolation logic exists in 4 places** (web AI Assistant, web NeuroOffice, mobile `buildAssistantContext`, and partially mobile `buildAgentContext`) — confirmed by direct code reading in Phase 0, re-confirmed live in Phase 1. A single shared sanitizer function, called from all 4, is the architectural fix Phase 3 should aim for rather than 4 separate patches.

## Deferred to "revisit before real money movement" (not fixed now, per scope)

- If transfer execution is ever added to chat, D2's write-ownership gap becomes far more dangerous — the same "write without ownership check" pattern applied to a balance-touching table instead of a conversation-storage table is a direct path to fund theft, not just history loss.
- The already-filed, separate finding from a prior session (`transfer_funds` trusting a caller-supplied `p_sender_id` with no `auth.uid()` check) compounds with any future AI-triggered transfer flow — if the AI ever gains a "send money" tool, that tool would need to pass the authenticated user's id, and this existing RPC gap means even a correct tool implementation sits on top of a currently-spoofable sender parameter. Worth closing before, not after, that capability ships.
- A1/A4-style phishing text embedded in transaction descriptions will remain visible to real recipients even after AI-side defenses are hardened — the AI Assistant correctly warning about it doesn't stop the same text from being visible to a user who never asks the AI about it. Not an AI-scope fix, but worth a product-level decision (e.g., description sanitization/flagging at write time, not just at AI-read time) once this is prioritized.
