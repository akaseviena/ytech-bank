# Переключение веба на книгу

29 октября 2026. Документ для веб-диалога. Закрывает KL-006.

Миграция базы уже сделана и проверена. Здесь — что меняется в коде
веб-приложения и чего делать нельзя.

---

## Что произошло, коротко

В проекте два приложения на одной базе: веб и мобильное. Они считали
деньги по-разному.

**Веб:** колонка `profiles.balance` плюс таблица `transactions`.
**Мобильное:** книга с двойной записью — `accounts`, `ledger_entries`,
`transfers`.

Это KL-006. Перевод, сделанный в приложении, в вебе не появлялся
и наоборот.

Хуже того: **два веб-источника не сходились между собой.** У части
счетов `profiles.balance` менялся без единой строки в `transactions`
(нагрузочные прогоны, тесты безопасности), у других в `transactions`
были движения, которых нет в балансе. Расхождение накопилось
за несколько месяцев, и заметить его было нечем — колонку с журналом
никто никогда не сравнивал.

**Решение: остаётся книга.** Не потому, что она новее, а потому что
`profiles.balance` — изменяемое число, и при расхождении нечем
доказать правильное значение. У книги сумма всех записей равна нулю,
и это проверяется запросом. Когда подключится Paynetics, сверять
их выписку можно будет только с книгой.

---

## Что уже сделано в базе

Миграции 011–014 применены. Проверено 29 октября в 15:14:

```
ledger_sum     = 0        книга сходится
mismatched     = 0        баланс каждого счёта равен веб-балансу
negative_main  = 0        отрицательных нет
imported       = 73       вся веб-история перенесена в книгу
adjustments    = 13       выравнивающих проводок
```

Вся история из `transactions` перенесена в `transfers` с
`rail = 'web'`. Расхождения между колонкой и журналом закрыты
проводками с `rail = 'migration'`.

**То есть книга сейчас содержит ровно то же, что показывает веб, плюс
то, чего веб не видел.** Переключение ничего ни у кого не изменит
в цифрах.

Отдельно применены 011 и 012: отозваны избыточные гранты у роли `anon`
на `profiles` и `transactions`, политики переведены с роли `public`
на `authenticated`. Если что-то в вебе перестало читаться — причина
может быть здесь, скажи, а не обходи.

## Схема книги

```
accounts
  id uuid pk, owner_id uuid, kind text, currency text,
  iban_display text, is_system bool, created_at timestamptz

  У каждого человека один счёт с kind='main'.
  Системные: bank_promo, bank_fees, bank_settlement (is_system=true).

account_balances            представление, не таблица
  account_id, owner_id, kind, currency, balance_minor bigint

transfers
  id uuid pk, idempotency_key text, from_account uuid, to_account uuid,
  amount_minor bigint, currency text, description text, category text,
  rail text, status text, failure_reason text,
  created_at timestamptz, completed_at timestamptz

ledger_entries              append-only, DELETE и UPDATE запрещены триггером
  id bigint pk, account_id uuid, transfer_id uuid,
  amount_minor bigint, currency text, created_at timestamptz
```

Функции:

```
post_transfer(p_from uuid, p_to uuid, p_amount_minor bigint,
              p_description text, p_category text, p_rail text,
              p_idempotency_key text)              security definer

search_transfer_recipients(q text)                 security definer
pounds_to_pence(numeric) returns bigint            immutable
```

## Главная опасность: единицы

**`profiles.balance` — numeric в фунтах. Книга — целое в пенсах.**

Это единственный источник ошибок, который реально выстрелит, и он уже
выстрелил дважды за время миграции. Один раз число уехало в сто раз,
второй раз — проверка, написанная с тем же допущением, это подтвердила
как успех.

Правила:

1. Перевод в пенсы делается **в одном месте**, функцией
   `pounds_to_pence`, и нигде больше. `* 100` в коде быть не должно.
2. Обратно — деление на 100 тоже в одном месте, при выводе.
3. Проверка такого преобразования пишется **по известному ответу**:
   £1 → 100, £0.01 → 1, £44.90 → 4490. Вторым вычислением того же
   самого проверять нельзя — оно разделит ошибку с первым.
4. Внутри приложения деньги не должны существовать как float вообще.
   Целое в пенсах, форматирование только на границе вывода.

## Что меняется в коде

| Было | Стало |
|---|---|
| баланс из `profiles.balance` | `account_balances.balance_minor`, счёт `kind='main'` по `owner_id` |
| история из `transactions` | `transfers`, где человек владеет счётом-источником или счётом-получателем |
| перевод через `transfer_funds` | RPC `post_transfer` |
| поиск получателей `search_recipients` | `search_transfer_recipients` |

**Чтения и записи переключаются в одном развёртывании.** Если
переключить записи раньше чтений, люди увидят замерший баланс
и решат, что деньги пропали.

---

## Ограничения, на которые натыкаются

Все три уже ломали мобильную сторону, не повторяй:

- **`transfers.category` объявлен NOT NULL.** Передача `null`
  роняет вставку. Подставляй значение, а не `?? null`.
- **`from_account <> to_account`** — перевод самому себе отклоняется.
- **`amount_minor > 0`** — ноль и отрицательные отклоняются.
  Направление задаётся парой счетов, а не знаком.
- **`rail` имеет CHECK со списком значений.** Для обычного перевода
  между людьми — `'internal'`. Новое значение требует расширения
  ограничения миграцией.

Ключ идемпотентности в `post_transfer` обязателен и обязан быть
устойчивым: двойное нажатие кнопки не должно переводить дважды.

## Чего пока нет на книге

Скажи, что из этого нужно, не придумывай сам:

- **`recent_recipients()`** работает по `transactions`. После
  переключения будет отдавать устаревшие данные. Нужен аналог
  по `transfers`.
- **Категории и аналитика**, если они построены на
  `transactions.category`.
- **Получатель в истории.** В `transfers` лежит `to_account`,
  а имя второй стороны закрыто политикой: чужие строки `profiles`
  недоступны. Функция `transfer_counterparties` для этого ещё
  не написана, это отдельная задача после переключения.

---

## Что делать нельзя

- **Писать в `profiles.balance`.** Нигде, никогда, ни одной строкой.
  После переключения на колонку встанет триггер, отклоняющий UPDATE.
- **Удалять `transfer_funds` до переключения.** Только после того,
  как новый путь проверен на живом приложении.
- **Писать миграции к книге.** Книгу ведёт мобильный диалог, номера
  миграций общие, встречные правки разойдутся. Если нужна миграция —
  скажи, какая, и почему.
- **Прогонять SQL самому.** Миграции запускает основатель в Supabase
  SQL Editor. Твоё дело — написать и объяснить.

---

## Порядок

1. Написать изменения, показать diff. Ничего не разворачивать.
2. Основатель прогоняет 013 и 014 ещё раз — за время работы в вебе
   появятся новые строки, их надо забрать и выровнять.
3. Сразу после чистой проверки — развернуть переключение.
   Не через час: веб продолжает писать в старую колонку, и разрыв
   между проверкой и переключением снова разведёт источники.
4. Проверить на живом: баланс в вебе совпадает с балансом
   в приложении, перевод из веба виден в приложении и наоборот.
5. После этого — заморозка `profiles.balance` и удаление
   `transfer_funds`, отдельными шагами.

## Как проверить, что получилось

```sql
-- книга сходится
select sum(amount_minor) from ledger_entries;   -- 0

-- баланс в вебе и в книге совпадает
select p.email,
       round(p.balance * 100)::bigint as old_pence,
       b.balance_minor                as ledger_pence
from profiles p
join account_balances b on b.owner_id = p.id and b.kind = 'main'
where b.balance_minor <> round(p.balance * 100)::bigint;
-- ноль строк до заморозки колонки

-- отрицательных пользовательских счетов нет
select count(*) from account_balances
where kind = 'main' and balance_minor < 0;      -- 0
```

Руками: перевод из веба появляется в приложении, перевод
из приложения появляется в вебе, суммы совпадают до копейки.
